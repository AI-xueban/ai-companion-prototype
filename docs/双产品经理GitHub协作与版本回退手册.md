# 双产品经理 GitHub 协作与版本回退手册

> 适用仓库：`AI-xueban/ai-companion-prototype`  
> 适用对象：两位主要使用 GitHub Desktop 维护原型、没有代码协作经验的产品经理

## 一、先记住 4 个概念

| 名称 | 可以理解成 | 使用原则 |
|---|---|---|
| `main` | 随时可演示的正式原型 | 不直接在这里试改功能 |
| 分支 Branch | 为一个需求复制出的独立工作区 | 一项需求建一个分支 |
| 提交 Commit | 一次有说明、可追溯的版本存档 | 做完一个完整小步骤就提交 |
| Pull Request（PR） | 请求把分支改动合回 `main` | 由另一位产品经理检查后合并 |

最重要的规则：**开始前先同步，修改前先建分支，合并前让另一人检查，出问题优先 Revert，不强制覆盖历史。**

## 二、一次性准备

两位产品经理分别完成：

1. 注册并登录各自的 GitHub 账号，不共用账号。
2. 由组织管理员邀请账号加入 `AI-xueban`，并给予该仓库写入权限。
3. 安装 GitHub Desktop。
4. 在 GitHub Desktop 登录自己的 GitHub 账号。
5. 打开 <https://github.com/AI-xueban/ai-companion-prototype>，选择 **Code → Open with GitHub Desktop**。
6. 选择各自电脑上的本地保存位置，点击 **Clone**。

不要通过微信、网盘反复传整个代码文件夹；GitHub 仓库是唯一协作源。

## 三、每次更新代码的标准流程

### 第 1 步：开始工作前同步 `main`

在 GitHub Desktop 中：

1. 左上角确认当前仓库是 `ai-companion-prototype`。
2. `Current branch` 选择 `main`。
3. 点击 **Fetch origin**。
4. 如果按钮变为 **Pull origin**，继续点击，直到显示已同步。

### 第 2 步：为本次需求新建分支

点击 **Current branch → New branch**，从最新 `main` 创建。

推荐命名：

```text
feature/student-one-lesson       学生端新功能
feature/admin-device-list        公司管理后台新功能
feature/teacher-class-report     教师端新功能
fix/student-login                问题修复
docs/review-rules                只修改文档
```

只使用英文小写、数字和短横线，不使用“最终版”“新版本2”等名称。

### 第 3 步：修改和自测

1. 确认 GitHub Desktop 顶部 `Current branch` 不是 `main`。
2. 修改原型或让 Codex 修改代码。
3. 启动受影响的应用，走完本次修改的核心路径。
4. 学生端、教师端、公司管理后台中未修改的入口也做一次基本检查。
5. 不提交账号密码、API 密钥、真实学生数据、`node_modules`、`dist`、ZIP 和日志。

### 第 4 步：分阶段提交版本

GitHub Desktop 左下角填写 Summary，然后点击 **Commit to 当前分支**。

推荐提交说明：

```text
学生端：增加小学一课一练入口
教师端：完善班级报告空状态
管理后台：调整设备列表筛选项
修复：解决切换教材后进度串联
文档：补充双人评审流程
```

一个提交只表达一件事。不要使用“改了”“更新”“最新版”这类无法追踪的描述。

### 第 5 步：发布分支并发起 PR

1. 点击 **Publish branch** 或 **Push origin**。
2. 点击 **Create Pull Request**。
3. 在 GitHub 填写：修改了什么、如何检查、有哪些已知问题。
4. 指定另一位产品经理为 Reviewer。

PR 描述模板：

```text
## 修改内容
- 

## 验证方法
- [ ] 核心流程已走通
- [ ] 学生端/教师端/管理后台相关入口未受影响
- [ ] 没有提交密码、密钥或真实用户数据

## 截图或演示地址
- 

## 已知问题
- 无 / 请填写
```

### 第 6 步：另一位产品经理检查并合并

检查重点：

- 页面和交互是否符合需求。
- 是否误改了另一端或公共组件。
- 是否出现空白页、按钮无响应、数据状态错误。
- 提交内容是否夹带无关大文件或敏感信息。

检查通过后选择 **Squash and merge**，让一次需求在 `main` 中保持为一个清晰版本。不要选择 Force push。

### 第 7 步：合并后双方重新同步

两人都回到 GitHub Desktop：

1. 切换到 `main`。
2. 点击 **Fetch origin / Pull origin**。
3. 确认新版本能正常启动。
4. 已合并的功能分支可以删除；历史提交不会因此丢失。

## 四、两人同时工作时怎样避免冲突

- 同一时间尽量分别负责不同应用或不同模块。
- 不要同时修改全局入口、根目录配置、公共路由、公共类型和同一个大文件。
- 必须修改同一文件时，先约定顺序：A 完成并合并，B 同步最新 `main` 后再开始。
- 每天开始和提交 PR 前都同步一次 `main`。
- PR 尽量小，建议 0.5～2 天内完成；不要积累一周后一次合并。
- GitHub 提示冲突时先停下，不要凭感觉点击覆盖，交给熟悉 Git 的人或 Codex处理。

## 五、版本存储与发布标记

普通提交已经是可回看的版本；对重要评审版再增加 Release/Tag。

推荐版本号：

```text
v0.1.0   第一个可完整评审版本
v0.2.0   增加一批新功能
v0.2.1   只修复问题
v1.0.0   对外正式演示基线
```

重要评审版合并到 `main` 并验证后：

1. 在 GitHub 仓库进入 **Releases → Draft a new release**。
2. 新建 Tag，例如 `v0.2.0`，目标选择 `main`。
3. 标题写版本名称，正文列出学生端、教师端、管理后台的变化。
4. 发布 Release。

建议至少给以下节点打 Tag：正式评审、客户演示、重要需求冻结、对外发布。

## 六、出问题时如何安全回退

### 情况 A：改动还没有提交

在 GitHub Desktop 的 Changes 列表中选中文件，使用 **Discard changes**。这会丢弃本地未提交内容，操作前必须确认文件不再需要。

### 情况 B：已提交到分支，但尚未合并

继续在该分支修复并新增一个提交；或者关闭 PR。不要为了“整理历史”强制推送。

### 情况 C：已经合并到 `main`，需要撤销整个需求

在 GitHub 打开已合并的 PR，点击 **Revert**，创建一个撤销 PR，由另一人检查后合并。

这是团队协作中最推荐的回退方式：原提交和撤销记录都保留，随时可以查明发生了什么。

### 情况 D：需要恢复到某个正式演示版本

找到相应 Release/Tag，请 Codex或熟悉 Git 的人从该 Tag 创建恢复分支，再通过 PR 合并。不要对共享 `main` 使用 `reset --hard` 或 Force push。

## 七、建议的仓库保护设置

稳定运行后，建议组织管理员为 `main` 开启 Branch protection：

- 必须通过 Pull Request 才能合并。
- 至少 1 人批准。
- 禁止 Force push。
- 禁止删除 `main`。
- 有自动检查后，再要求检查通过才能合并。

只有两位产品经理时，保留一位 Backup Owner，避免唯一管理员账号丢失导致仓库无法管理。

## 八、提交前 30 秒检查表

- [ ] 我当前不在 `main`，而是在本次需求分支。
- [ ] 修改内容只属于一个需求。
- [ ] 核心页面已经打开并操作过。
- [ ] 没有密码、密钥、真实个人信息和内部敏感数据。
- [ ] 没有 `node_modules`、`dist`、ZIP、日志和无关大文件。
- [ ] 提交说明能让另一位同事看懂。
- [ ] 合并前已由另一位产品经理检查。
- [ ] 重要评审版本已创建 Release/Tag。

## 九、遇到以下情况先停止操作

- GitHub 显示 Merge conflict。
- 不确定自己是否正在 `main` 上修改。
- 页面出现大量不属于本需求的改动文件。
- GitHub 要求 Force push、覆盖远端或删除分支历史。
- 发现密码、密钥或真实用户数据已经提交。
- 拉取后项目突然出现大范围异常。

此时保留现场，不要反复点击；把 GitHub Desktop 截图和当前分支名称发给协助人员处理。
