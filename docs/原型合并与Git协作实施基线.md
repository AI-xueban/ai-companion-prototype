# AI 学伴原型合并与 Git 协作实施基线

> 文档状态：合并前产品基线  
> 适用对象：产品经理、原型维护者、协助建仓/部署的 IT 同事  
> 当前阶段：只确定合并规则和执行顺序，尚未修改现有原型代码

## 1. 背景与目标

当前目录包含两套同源但已分别演进的学生端原型，以及平台运营后台、教师端和学生端工程内的内部管理页面。目标不是开发正式 App，而是建立一套可以长期维护、持续演示、支持两位产品经理共同迭代的高保真原型。

本次合并要实现：

1. 学生端只保留一个可运行原型，在同一原型内切换小学和初中学段。
2. 小学、初中的差异由学段规则控制，不再维护两个完整学生端副本。
3. 平台运营后台和教师管理平台纳入同一 Git 仓库，但保持独立应用入口。
4. 两位产品经理通过私有 Git 仓库、功能分支和合并检查共同维护。
5. 历史 ZIP、单 HTML 和旧目录只作归档，不再作为后续开发源代码。

## 2. 已确认的产品决策

### 2.1 学生端统一原则

- 合并后只有一个学生端原型。
- 学段、学制、年级、学期和教材版本继续从“我的课本”统一维护。
- 小学与初中共用五 Tab、用户身份、成长数据和基础壳层。
- 首页学习入口、学科列表、教材目录和练习流程根据当前学段自动切换。
- 切换学段后不清空另一学段的演示进度。

### 2.2 首页学习入口

| 当前学段 | 首页入口一 | 首页入口二 | 入口二交互来源 |
|---|---|---|---|
| 小学 | 同步课堂 | 一课一练 | `学生端原型`中的一课一练/课后练底层交互 |
| 初中 | 同步课堂 | 精准练习 | `AI学伴_0812/ai_friend_v2.0`现有交互 |

小学“一课一练”主路径：

```text
首页点击一课一练
→ 选择学科
→ 选择教材、单元和课时
→ 选择题量
→ 进入答题
→ 查看结果
→ 返回原入口
```

保留原交互中的单元测、练习状态、题量选择和题库不足处理，但不再保留“课后练”这一独立产品名称或独立导航入口。

### 2.3 指定采用“学生端原型”交互的模块

以下模块的小学和初中交互均以 `学生端原型` 为准：

| 模块 | 采用内容 | 处理方式 |
|---|---|---|
| 智阅作业 | 拍照、裁剪、多页拍摄、扫描批改、结果、历史记录 | 整条流程迁入合并版 |
| 个性化学习 | 计划向导、关卡路径、继续学习、历史计划、完成状态 | 迁入并适配统一学段与教材状态 |
| 爱心公益 | 学生端入口、项目、捐赠、记录、证书/成果等交互 | 以该原型交互为准，同时核对跨端状态规则 |
| 万象视界 | 首页、频道、内容详情、每日一词、短视频、搜索、爱心公告栏 | 以该原型交互为准 |

迁移时不得直接覆盖同名文件。应逐模块迁移页面、数据和状态，再接入合并版入口。

### 2.4 不再单独保留的功能

| 内容 | 决策 | 备注 |
|---|---|---|
| 课前学 | 不作为独立功能保留 | 所需看课能力并入“同步课堂” |
| 课后练 | 不作为独立功能保留 | 所需交互用于小学“一课一练” |
| 原型标注工具 | 不迁入合并版业务原型 | 避免评审工具污染演示界面 |
| 旧教师花名册 | 不恢复 | 教师端以现有新版教师平台为准 |
| 旧热力图 | 不恢复 | 同上 |
| 旧课程管理 | 不恢复 | 同上 |

“不保留页面/入口”不等于删除其依赖的数据。若数据仍服务小学或其他保留流程，应独立迁移。

### 2.5 必须保留的小学数据

- 小学语文、数学、英语、道德与法治、科学的学科配置。
- 小学科学知识目录和知识点数据。
- 小学教材目录、版本、年级和学期数据。
- 小学视频样例及视频匹配规则。
- 小学一课一练题目、题量、练习状态和题库不足演示数据。
- 小学专属页面仍在使用的必要 mock 数据。

不应把小学数据永久绑在旧页面组件中。迁移时应放入合并版的 `data/` 或 `services/`，由小学业务页面读取。

## 3. 合并后的产品结构

### 3.1 建议仓库结构

```text
ai-companion-prototype/
├─ apps/
│  ├─ student/          # 小学、初中共用的学生平板原型
│  ├─ admin/            # 平台运营后台
│  └─ teacher/          # 教师管理平台
├─ docs/
│  ├─ current/          # 当前有效产品文档
│  ├─ decisions/        # 合并取舍与关键决策记录
│  └─ archive-index/    # 历史文档索引，不复制大量发布物
├─ scripts/             # 构建、打包和发布脚本
├─ README.md
└─ .gitignore
```

三个应用进入同一 Git 仓库，但分别启动、构建和发布。学生端不嵌入运营后台；教师端不与平台运营后台共用一套业务菜单。

### 3.2 管理侧边界

| 应用 | 主要用户 | 合并范围 |
|---|---|---|
| 平台运营后台 `admin` | 平台运营、内容和设备管理人员 | 设备管理、万象视界内容运营、金币、商城兑换、捐赠与爱心池、规则、月报与公示 |
| 教师管理平台 `teacher` | 教师、班主任、教研人员 | 仪表盘、学情分析、学生管理、班级激励、消息、教师资料 |

学生端工程中的 `InternalAdminApp` 属于平台运营能力，应迁入 `admin`；`TeacherApp` 保持为独立教师应用。

## 4. 统一学段状态与数据隔离

### 4.1 统一学业上下文

合并版至少需要维护以下上下文：

```text
schoolStage   小学 / 初中
schoolSystem  六三制 / 五四制
grade         年级
term          上学期 / 下学期
subject       学科
textbook      教材版本
```

当前代码主要依赖“年级 + 学制”反推小学或初中。合并时建议形成明确的 `schoolStage` 派生值或统一判断方法，禁止各页面自行判断学段。

### 4.2 进度隔离键

教材、看课和练习进度至少按以下组合隔离：

```text
学段 + 学制 + 年级 + 学期 + 学科 + 教材版本
```

智阅作业、爱心公益和万象视界等跨学段共用能力，可复用账号级 mock 状态；涉及教材和题目的状态必须按学业上下文隔离。

### 4.3 切换学段后的刷新规则

从“我的课本”切换小学/初中后，应立即完成：

1. 首页右侧入口切换。
2. 学科 Tab 的学科列表和默认科目切换。
3. 教材目录和视频数据切换。
4. 错题学科列表切换。
5. 关闭仍引用旧学段教材的学习页、答题页或弹层。
6. 保留另一学段已产生的演示进度，切回时恢复。

## 5. 模块迁移清单

### 5.1 第一优先级：建立可合并底座

| 工作项 | 来源 | 目标 | 验收 |
|---|---|---|---|
| 建立干净仓库结构 | 新建 | 根仓库 | 三个应用目录清楚，发布物未进入 Git |
| 迁入学生端基础壳 | v2.0 | `apps/student` | 五 Tab、登录、测评和学段切换可运行 |
| 统一学业上下文 | 两边整合 | `apps/student` | 小学/初中切换后入口、学科、教材同步变化 |
| 迁入小学数据 | `学生端原型` | `data/`、`services/` | 小学科学、教材、视频和练习数据可读取 |

### 5.2 第二优先级：首页学习入口

| 工作项 | 验收 |
|---|---|
| 小学显示“同步课堂 + 一课一练” | 小学任一年级进入首页均显示两个入口 |
| 初中显示“同步课堂 + 精准练习” | 六三制和五四制初中均正确显示 |
| 小学一课一练全流程 | 能选科、选教材课时、选题量、答题并返回 |
| 初中精准练习不回退 | 保持 v2.0 当前选题与答题流程 |

### 5.3 第三优先级：四个指定模块

建议迁移顺序：

1. 智阅作业：边界相对独立，适合先验证迁移方法。
2. 万象视界：页面较多，并与运营后台配置概念联动。
3. 爱心公益：涉及学生端与平台后台跨端状态。
4. 个性化学习：与学科、教材、任务、答题和进度耦合最深，最后迁移。

### 5.4 第四优先级：管理平台归并

1. 以 `后台原型/prototype` 为运营后台外壳。
2. 把学生工程内 `InternalAdminApp` 的金币、兑换、捐赠、爱心池、规则、月报能力按菜单迁入。
3. 合并同名“捐赠与爱心池”时，以最新跨端需求文档为产品规则，不按页面整体覆盖。
4. 教师端单独运行，只与学生端共享必要的 mock 业务口径，不共享页面状态。

## 6. Git 协作方案

### 6.1 建仓原则

- 新建公司私有远程仓库，不直接扩大当前混有大量数据和历史产物的 `AI学伴_0812` 仓库。
- 当前三个原型目录完整保留为迁移来源和只读备份。
- 新仓库只迁入有效源码、当前文档和必要的小体积演示资源。
- `node_modules/`、`dist/`、ZIP、日志、临时文件、密钥和生成报告不提交。
- 大型必要媒体若数量继续增长，再评估 Git LFS；初期不要把全部历史素材直接导入。

### 6.2 双人协作分支

```text
main
├─ feature/student-primary-practice
├─ feature/student-zhiyue-homework
├─ feature/student-discovery
├─ feature/admin-charity
└─ docs/product-decision-xxx
```

- `main` 始终保持可启动、可演示。
- 一项功能使用一个短期分支。
- 合并前由另一位产品经理完成页面演示检查。
- 不建议两人同时修改 `App.tsx`、全局菜单、学业上下文或公共类型。
- 必须同时改公共文件时，先约定一人完成壳层接入，另一人只改独立模块。

### 6.3 提交规范

建议使用中文、动作明确的小提交：

```text
学生端：接入小学一课一练入口
学生端：迁入小学科学教材数据
智阅作业：完成拍照到裁剪流程
后台：合并爱心项目公示状态
文档：确认小学与初中首页入口规则
```

不使用“改一下”“更新代码”“最终版”等无法追踪内容的提交说明。

## 7. 是否需要 IT 介入

需要 IT 一次性提供基础条件，但不需要 IT 负责产品原型的日常迭代。

建议 IT 协助：

1. 创建公司私有 GitLab、Gitea 或其他合规的私有仓库。
2. 为两位产品经理开通读写权限和账号恢复机制。
3. 确认是否允许使用 GitHub 等外部托管平台。
4. 配置仓库备份。
5. 提供静态演示地址；条件允许时配置合并到 `main` 后自动发布。

产品经理负责功能分支、提交、合并验收和版本说明。

## 8. 阶段验收标准

合并版学生端完成的最低标准：

- 同一入口能演示小学和初中。
- 小学首页显示“一课一练”，初中首页显示“精准练习”。
- 两种学段的同步课堂、学科列表、教材和练习范围正确。
- 小学科学及小学专属数据仍可被实际页面读取。
- 智阅作业、个性化学习、爱心公益、万象视界均采用已指定的交互版本。
- 删除的旧入口不会在导航、演示控制器或页面中重复出现。
- 学段切换后不会把小学进度写入初中，反之亦然。
- 学生端、运营后台和教师端均可独立启动和构建。
- 两位产品经理可从远程仓库拉取、创建分支并完成一次合并流程。

## 9. 实施边界

本轮合并只服务高保真原型维护：

- 允许使用 mock 数据、浏览器本地存储和前端状态模拟跨端联动。
- 不要求建设真实服务端、账号系统、接口鉴权或云端进度同步。
- 不为了“像正式产品工程”而提前做大规模基础设施重构。
- 但必须保证目录、数据归属和 Git 协作规则足够清晰，以便后续持续迭代。
