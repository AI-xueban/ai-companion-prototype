# AI伴学 V2.0 协作约定

## 工作目标

这是一个 React + Vite + TypeScript 的学生端产品原型。优先在不破坏现有交互和演示数据的前提下，完成明确、可验收的产品或视觉改动。

## 开始任务前

1. 先读取 `ARCHITECTURE.md`，再读取与本需求对应的 `docs/v2.0/` 文档。
2. 根据架构地图的“常见改动最小阅读范围”定位文件；默认只读目标文件、直接父/子组件、必要的类型或状态服务。
3. 不扫描或读取 `node_modules/`、`版本保存/`、原始知识图谱大数据、构建产物、PDF/截图，除非任务明确要求。
4. 开始改动前简短列出：目标文件、直接影响的共享状态、验证方式。若必须扩大阅读范围，说明原因后再扩展。

## 强制工作流：先读后改

每个需求按以下顺序执行；没有完成前一项，不进入下一项。

1. **归类需求**：判断它属于页面视觉、单模块交互、跨模块流程、共享数据/状态或工程配置。不能根据一句“优化一下”直接开始改代码。
2. **查地图定位**：读取 `ARCHITECTURE.md` 的“快速入口”“业务模块索引”和“常见改动的最小阅读范围”，确定代码起点。
3. **最小读取**：按“目标文件 → 直接父/子组件 → 直接类型或数据/状态服务”的顺序读取。每次读取只为回答一个问题：页面在哪里、交互从哪里进出、数据由谁维护。
4. **影响面确认**：在改动前明确列出目标文件、可能受影响的入口、共享状态与不应触碰的边界。若发现会影响教材、进度、奖励、Tab、路由/旅程或浏览器存储，必须补读对应服务和 `App.tsx` 的相关回调。
5. **最小修改**：优先在业务模块内完成改动；只有跨页面编排或全局状态确有必要时，才修改 `App.tsx`。不夹带无关重构、格式化或清理。
6. **按风险验证**：先验证改动页面和入口；再按“验证规则”决定是否运行类型检查或构建。记录验证结果后交付。

### 阅读扩展门槛

只有出现以下情况才能扩大阅读范围：

- 目标组件的 props、回调或类型无法解释当前交互；
- 改动涉及跨 Tab 跳转、全屏层、底栏显示/隐藏或学习回流；
- 改动涉及年级、学期、教材版本、同步学习进度、奖励、错题或本地持久化；
- 类型检查或页面验证显示直接依赖存在问题。

扩大阅读时按依赖链逐层增加文件；禁止为了“先熟悉项目”全仓通读。若需要读取超过 12 个业务源码文件，先停下并说明新增范围与原因，等待确认或把任务拆成两步。

### 不可默认推断的事项

- 不要把产品需求文档、历史版本或页面名称当作当前代码已实现的证据；先核对当前模块。
- 不要假设 mock 数据、localStorage key、接口适配层或宣传页与学生端主流程同步。
- 不要为了消除局部重复而改动公共组件、全局样式或构建配置；除非需求明确要求且影响面已确认。

## 修改规则

- 保持 `App.tsx` 只做场景编排。局部页面样式或交互不要无必要地新增全局 state。
- 年级、学期、学制与教材版本只通过“我的 → 我的课本”及相关存储服务变更；首页和学科顶栏是只读展示。
- 涉及同步学习时，保留以“学科 + 版本 + 年级 + 学期”为维度的进度隔离。
- 涉及奖励时使用既有奖励服务与 `onRewardGranted` 回调，不直接修改展示数值。
- 新增浏览器持久化 key 时，同步维护 `services/demoStateService.ts`，让演示重置能清理该 key。
- 新增 mock / 规则数据优先放在 `data/` 或 `services/`，不要堆进页面组件。
- 保留平板舞台尺寸和单文件构建策略；除非明确要求，不改 `config/appConfig.ts`、`vite.config.ts`。
- 不修改 `promo/`、历史版本或根目录的数据处理工具，除非用户明确点名。

## 验证规则

- 仅调整视觉或文案：检查目标页面及受影响的直接入口。
- 改共享类型、入口、状态服务、构建配置：运行 `npm run typecheck`；必要时再运行 `npm run build` 或 `npm run check`。
- 若验证失败，区分本次改动导致的问题与工作区原有问题，绝不用重置或覆盖其他人的修改来“修复”。

## 交付格式

完成后简洁汇报：修改的文件、实现结果、执行的验证与结果、未处理的风险或后续项。不要复述无关文件，也不要把历史版本当作当前实现依据。
